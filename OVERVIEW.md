# Paseo Factory

One Paseo plugin that merges **Roles**, **Blueprints**, **Leases**, **Warden** and **Inbox**. Each module is a tab of the Factory screen and can be switched off in the Factory settings. One MCP server, `factory`, serves all their tools; one git source feeds roles and blueprints.

| Module | Tab | What it does | MCP tools |
|---|---|---|---|
| Roles | Roles | Agent roles from git (`PASEO_AGENT_ROLE=<name>`) | none (hook) |
| Blueprints | Blueprints | Flows: stages name roles, verdicts pick the next stage | `blueprint_list`, `_start`, `_status`, `_verdict`, `_retry`, `_abort`, `_resume`; `usage_limit_status`, `_classify`, `_lift` |
| Leases | Leases | One agent at a time on a named resource | `lease_acquire`, `_renew`, `_release`, `_list` |
| Warden | Warden | Pings agents that go quiet; supervises subagents | `warden_register`, `_register_subagent`, `_update`, `_done`, `_list` |
| Inbox | Inbox | Multiple-choice questions and approvals for the human (2 to 4 options, an open "Other" always added) | `inbox_ask`, `_status`, `_list`, `_withdraw`, `_pending`, `_answer` |

Inbox setting `notifyMailTo` (default empty = off; e.g. `@pm`): one short mail per NEW item of any asker (id, asker, kind, option labels, first 300 chars of the question; never the context), once per item, persisted. Blueprint-gate items are skipped while blueprints `events.mailTo` is set (the run's "waiting" mail already names the item).


There is no data migration. Setting `importLegacyState` (off by default) copies the state file of the old stand-alone plugin (`agents-leases`, `agents-warden`, `agents-inbox`) once, for a module that has no Factory state yet.

## Supervisor

A sixth tab (between Overview and Activity) for the **Supervisor**: ONE on-demand agent per Factory (role `supervisor`, label `paseo.factory.supervisor=1`, created without a kube template so it runs on the daemon; its id is kept in `supervisor.json`). It runs only while the Factory needs it: a run starting, a request (`supervisor_ask`), a message from the tab, a digest with new problems or an extension crash wake it (a new session is created, briefed from the Factory's store); after `idleArchiveMinutes` (default 10; 0 = always on) with nothing busy (no active run, live stage agent, unanswered request, undelivered digest or mid-turn) it is asked for a handoff (`supervisor_note`, one turn, 60 s cap), then the agent AND its workspace are archived. Its notes (8 KB), sessions (20), request log and queue live in `supervisor.json`, not in the agent. While archived a no-LLM watcher keeps the digest going: failed runs and extension crashes wake it, repeats and lease contention only raise a flag (tab badge and a mail to the supervisor `reportTo`, if set). The tab shows "Archived (idle)" with "Wake now", the current session's conversation, "Previous sessions" and the request log. A PM supervises one run; the Supervisor supervises the Factory: runs paused, failed or waiting for a PM that does not exist, spawn failures, lease contention and expiry, extension health, role and blueprint load errors, git sync errors, Warden escalations. The Factory sends it a debounced "Factory digest" (a problem is told once, again after `repeatMinutes` while open); it acts with `blueprint_abort/_retry/_resume`, asks the user with `inbox_ask`, and changes roles or blueprints only through pull requests on their git source.

- Open to every agent: `supervisor_ask(question)` relays your question (with your agent name) and returns the answer, or a request id to poll with `supervisor_ask_status` (`queued` while the Supervisor wakes, then `pending`, `answered`; the 120 s wait starts once the request reached the agent); `supervisor_status` shows its state and stable agent id (steer it directly with a normal agent message too).
- Supervisor only: `supervisor_reply(request, answer)`, `supervisor_note(text)`, `extension_restart(id)`. A restart calls `POST <callback>/restart` on the extension (extensions opt in; 404 means unsupported) and is allowed once per hour per extension.
- Settings: `enabled` (default true; false: the Supervisor is never started or woken, an agent still running is archived at the next digest tick, `supervisor_ask`/`supervisor_status` say "Supervisor disabled; its notices go to the blueprints events.mailTo (else the supervisor reportTo)", the tab shows Disabled, and expired leases and dropped extensions are mailed once each to the blueprints `events.mailTo`, or to `reportTo` when the Blueprints module is off), `reportTo` (default empty = no mail: where the Supervisor's flags go, e.g. `@ops`), `autoStart` (automatic wake-ups; off: only asks, chat and Wake now), `idleArchiveMinutes`, `cwd` (or `FACTORY_DEFAULT_CWD`), `role`, `defaultProvider`, `digestSeconds`, `repeatMinutes`, `askTimeoutSeconds`. The tab embeds the Supervisor's normal agent conversation (the app's own thread and composer; requests from agents show as ordinary messages), status, watched problems and a Start / Restart / Wake now button. Restart archives the old agent and its workspace. `PASEO_SUPERVISOR=off` skips the supervisor tools for an agent.

## Warden is for Factory agents only

`warden_register`, `warden_register_subagent` and `/warden` refuse any agent without the label `paseo.factory=1` (the label the Factory puts on its workers and PM; extensions that spawn agents should add it, and set `PASEO_WARDEN=on` in their env so Warden is injected). The `warden_*` tools are hidden from other agents (`inbox_answer` likewise from agents without a trusted label, setting `trustedLabels`). Warden's setting `scope` defaults to `factory`; every minute it also drops watches of archived or vanished agents and of non-Factory agents.

## Layout

Source lives in `client/`, `server/` and `shared/` only (Paseo's plugin loader requires it); each module has a subfolder in each (`server/warden`, `client/warden`, `shared/warden`). `layout.test.ts` checks this in CI.

## Git source

Roles and blueprints come from one git source (Roles tab settings): `url`, `ref`, and `path` = the **Factory folder**, whose subfolders are `roles/`, `blueprints/`, `crons/` (`crons/schedules.json`, see Crons), `leases/`, `warden/`, `inbox/`. Example: `services/paseo/plugins/factory`. Every workspace the Factory creates runs on the Factory setting `runtime`: `local` (the default, on the daemon) or the id of a workspace runtime plugin such as `kubernetes`. A role passes options to that runtime with `runtimeOptions` (for example `{ profile: coordinator }`; the older `runtimeProfile` is still read for one release) and other plugins' defaults with `plugins.env` (the older `plugins.kubeTemplate` is still read for one release as `PASEO_KUBE_TEMPLATE`). Roles are `roles/<name>.yaml` ([format](role.schema.json), examples in `shared/examples/roles`); blueprints are `blueprints/<name>.toml` (examples in `shared/examples/blueprints`). A role can set `runtimeProfile` (a Kubernetes Runtime pod profile name, `^[a-z][a-z0-9-]{0,31}$`, e.g. `runtimeProfile: small` for roles that build nothing): the Factory passes it as the Runtime option `profile` when it creates the worker's workspace, which wins over the Runtime's `projectProfiles`. It is ignored on the `local` runtime, when the role omits it, and when a worker joins an existing shared workspace. Per-stage overrides are not supported: set it on the role.

## Blueprints

```toml
version = 1
name = "ticket"
confirm = ["ticket"]            # must be checked for real; start passes ticket_confirmed = "true"
pm_extra_max = 2                # the PM's one judgement may grant at most this many extra attempts
[vars.ticket]
required = true
pattern = "^[A-Z]+-[0-9]+$"

[[stage]]
id = "implement"
role = "implementer"            # PASEO_AGENT_ROLE of the worker
prompt = "Implement {{ticket}} ... {{stage.investigate.summary}}"
max_attempts = 3                # tries per entry; a turn that ends without a verdict uses one
max_runs = 50                   # entries over the run (loops)
flake_retries = 1               # free retries; also raises the infra-flake bound (setting `flakeRetries`, default 3); any failed turn is retried for free up to it
facts = "pr"                    # show PR facts; data.pr_urls is checked on GitHub
[stage.on]
done = "qa"                     # verdict -> next stage ("done" and "failed" end the run)
blocked = "ask-blocked"
exhausted = "pm"                # PM judgement, once; or a stage id, or "failed"
[stage.verify]
done = ["exists", "open"]       # facts GitHub must confirm before the verdict is accepted
```

Stage kinds: `agent` (default), `gate` (question or approval through the Inbox; `pr = ...` ties it to PR heads, `criteria = ...` is hashed and an identical approval is reused, `store_as` saves a typed answer into a variable, `note_to` adds it to another stage's prompt, `wait = "merge"` with `pr` and `expires_in_minutes` is a passive wait with no Inbox item: `on.merged` when GitHub shows every PR merged, `on.head_moved` if a head moves first, `on.expired` after the timeout; `pm = true` spawns the run's on-demand PM, which may answer that gate and no other), `call` (a tool such as `release_request`; a Factory or extension tool is called directly, any other by a short-lived worker of the stage's `role`), `blueprint` (a child run, `at` enters it mid-way), and any kind an extension provides. `skip_if = "{{x}} == y"` needs an `on.skipped` edge. `skip_if_merged = "<stage>"` (any kind) reads that stage's `data.pr_urls` fresh on entry: when every PR is already merged, the stage is not run and `on.already_merged` is followed (for example to the release), so merged code is not babysat, implemented or QA-ed again and no person is asked about it. A merge wait (`wait = "merge"`) whose PRs are all merged or still in a merge queue when `expires_in_minutes` is up is re-armed for another `expires_in_minutes` (`merge_wait_rearmed` in the history) instead of following `on.expired`; a PR that left the queue, or auto-merge on a red head, still expires. An agent stage with `worktree_check = <seconds>` checks that a freshly spawned worker's checkout answers `git rev-parse` within that time, counted from when its workspace is up (the probe's shell prints its first line there; an open terminal is not enough, its shell may only start with the pod), not from the spawn: a cold pod has `worktree_boot_grace` seconds (default 600) to boot first, and one still not up by then is logged `worktree_unchecked`, not counted as a failure. No answer, or not a worktree, archives that worker and its workspace and starts one fresh worker; a second failure pauses the run with the reason. A gate with `expires_in_minutes` and `default_answer = "<option>"` takes that answer by itself when nobody answered in time (logged as "by default") instead of following `on.expired`. `agent = "reuse:<stage>"` sends the task to that stage's worker (a replacement with the same role if it is gone).

Runs are JSON in `~/.paseo/plugin-data/paseo-factory/blueprints.json`, written before every transition; after a daemon restart, running stages are re-dispatched, open gates re-read. Workers are created with `PASEO_AGENT_ROLE`, `PASEO_FACTORY_RUN` and the labels `paseo.factory=1`, `paseo.factory.blueprint`, `.run`, `.stage`, `.role`; every worker gets a Warden task. The Blueprints tab shows one card per run.

PM tools (`blueprint_start` ...) are injected into agents whose `PASEO_AGENT_ROLE` equals the `pmRole` setting (default `pm`) or that have `PASEO_FACTORY_BLUEPRINTS=on`; stage workers get `blueprint_verdict`, `blueprint_status`, `blueprint_waiting` and `blueprint_progress` (saves one step's result in the run store; a replacement worker of the same stage entry, after a pod eviction or a lost session, gets the saved results in its prompt and does only the missing steps; cleared when the stage is entered again); an on-demand run PM (`PASEO_FACTORY_STAGE=pm`) gets `blueprint_status`, `_retry`, `_resume`, `_abort` and `blueprint_pm_escalate`, `_answer`, `_done`. `blueprint_retry`, `_resume` and `_abort` are for the run's PM, its starter and agents labelled `paseo.assistant=1`.

## Spend, timelines and flows

The Overview tab (first, default) is a read-only dashboard: blueprint runs (failing or stalled highlighted), pending Inbox items, leases, Warden attention, live role agents, git sync status, extension health, recent activity and **Spend**. Spend aggregates Paseo's per-turn usage (`lastUsage`: tokens and `totalCostUsd`), recorded at each `agent.turn_ended` of agents the Factory spawned (label `paseo.factory=1`), per run, role and day (RPC `blueprints.spend`, stored in `spend.json`). Each run card has a **Timeline**: time per stage, working vs waiting, dispatches and retries, gate open/close times and escalations, built from the run's saved history. Next to Timeline, **Flows** (default view stays Timeline) draws the run as a graph: stages (agents) as nodes, verdict transitions as edges, the path taken highlighted, live state and child runs; on a blueprint template it shows the static shape.

## Activity, diffs, transcripts

The **Activity** tab is a factory-wide feed (runs, stage changes, gates, escalations, leases, Inbox items, merges, and what extensions report) with filters by type, blueprint and role. Extensions add events with `POST /extensions/event` `{ id, type, tone?, title, detail?, link? }` (bearer = endpoint token): `type` is the extension's own label (for example `deploy`; lowercase letters, digits, `-` and `_`, at most 24; a malformed one or a Factory kind other than `merge` shows as `extension`) and gets its own filter chip, `tone` (`success`, `warning`, `danger`; default muted, `merge` success) colours its badge. Run cards show each PR's diff summary (files, +/−, read with `gh pr view`) and a link to the full diff, and an expandable read-only "latest messages" peek of the stage's agent (also in Roles › Agents).

## Start endpoint (Events plugin)

The Factory writes `~/.paseo/factory/endpoint.json` (mode 0600, `{url, token}`) and serves on loopback only, with the token as a bearer:

- `POST /blueprints/start`, body `{blueprint, vars, requestedBy, idempotencyKey}` → `200 {runId}`, `404` unknown blueprint, `400` bad vars, `401`. The same `idempotencyKey` returns the same run.
- `GET /blueprints/runs?since=<epoch ms>&has_var=<name>` → `200 {runs}`: runs updated since then (optionally only those with that var set), each with `id`, `blueprint`, `status`, `parent`, `vars`, `updatedAt`, `endedAt`, each stage's `status`/`verdict`/`summary`/`data`, the kinds of `events` in its history, and where it stands now: `stage`, `waitingFor`, `pmPending`, `suspended` (`{reason, since, by}`), the open `gate` of the current stage (`{stage, itemId, kind: approval|question|merge, openedAt, passive}`; `itemId` is the Inbox item, null for a passive merge wait), the open `escalations` (Inbox item ids), the current stage's worker `agentId` and `role`, and `prs`: per PR URL the run refers to, the last facts the Factory read from GitHub (`state`, `head`, `ci`, `review`, `mergeable`, `draft`, `queued`, `queuePosition`, ..., and `checkedAt`). Read-only: the endpoint never calls GitHub itself. For plugins that follow runs (for example Slack feedback in paseo-factory-slack, the tickets-dispatcher's Tickets tab).
- PR facts go through one per-URL cache: a fact younger than 2 min is served from memory, a merged PR is kept (and a closed one until a forced read) while a stored run refers to it, concurrent lookups of a URL share one `gh` call, and at most 4 run at once. Gates that need the current head (opening a gate, checking an answer, `verify`, a PR in the merge queue) read GitHub now.
- `GET /blueprints` → names, descriptions and variables (`required`).

## Crons (Blueprints module)

The **Crons** sub-tab of Blueprints (Runs | Templates | Crons | Quota | Settings) starts blueprints on cron schedules, with at most one active run per schedule.

- **Where schedules live:** `crons/schedules.json` in the Factory folder of each git source (next to `roles/` and `blueprints/`, synced with them), plus the Blueprints setting `crons.schedules` (same entries; it wins on a repeated id, then sources in order). A file that does not parse keeps its last good copy; a bad entry is left out and shown in the tab.
- **Format:** `{"schedules": [{"id": "nightly", "cron": "0 9 * * 1-5", "timezone": "Europe/Paris", "blueprint": "my-blueprint", "vars": {}, "enabled": true, "maxFailures": 2, "mailTo": "@ops"}]}`. `id` is lowercase letters, digits, `-` and `_`; `cron` has 5 fields (minute hour day-of-month month day-of-week, with `*`, lists, ranges and steps; day of week 0-7, Sunday 0 or 7; both day fields restricted means either matches); `timezone` is an IANA zone (default `UTC`); `vars` are strings; `enabled` defaults to true, `maxFailures` to 2; `mailTo` replaces `crons.mailTo`.
- **Start:** each Blueprints tick (`pollSeconds`) looks at the minutes since the last tick, at most the last 10, and starts only the latest matching one. The run gets the vars plus `cron_id` and `cron_slot` (the UTC minute, `2026-10-29T08:00Z`), `requestedBy` `cron:<id>` and the idempotency key `cron:<id>:<slot>`, so a slot starts at most one run, across restarts too. The blueprint must declare `cron_id` and `cron_slot` (with `default = ""`). A slot is skipped and logged while a run with that `cron_id` has not ended. A suspended Factory or a cold catalog retries the slot within the window.
- **Pause:** a run of the schedule that ends failed or aborted, or a start the engine refuses (no such blueprint, bad var), counts as a failure; `done` resets the count. At `maxFailures` in a row the schedule pauses and ONE mail goes to its `mailTo` (or `crons.mailTo`; empty: only logged), and the Supervisor sees it. It resumes with **Resume** in the tab, or when its `enabled` goes from false to true. **Pause** in the tab stops it by hand (no mail).
- **Run now:** starts the blueprint at once with the same vars, unless a run of the schedule is active; key `cron:<id>:now:<minute>`. Its outcome counts like a scheduled run's. It works even with crons off.
- **The tab** lists each schedule: cron and zone, blueprint, source, state (on, disabled, paused, crons off), next run, active run, last run and its result, failures in a row; with Pause/Resume and Run now.
- **Settings (Blueprints):** `crons.enabled` (default **false**: nothing starts on its own until you switch it on, so installing this version changes nothing while another scheduler still starts the same blueprints; turn the other one off first), `crons.mailTo`, `crons.schedules`.
- **State:** `crons.json` in the Factory's data folder (last minute evaluated; per schedule the failures, pause, last slot and the runs it follows), written atomically. RPCs: `blueprints.crons.list`, `.pause`, `.resume`, `.run_now`.

## Inbox and trusted agents

Factory setting `trustedLabels` (list of `"key=value"`, default empty = no agent is trusted): an agent carrying one of these labels, such as an assistant acting for the user (e.g. `["paseo.assistant=1"]`), is trusted. `inbox_pending` lists every pending item and `inbox_answer(item, answer)` answers one; both are for trusted agents (others see only their own items and cannot answer). A trusted agent may also withdraw the Factory's own Inbox items, steer any run (`blueprint_retry`, `_resume`, `_abort` beside its PM), use the whole-Factory operations (`all: true`, `attach_agent`), and its workspace is never taken by the orphan sweep. The answer is recorded as "answered by the Assistant on behalf of the user".

## Reports, exclusions, roadmap

- **Reports go through Agents Mail when it is installed.** Information the Factory sends to an agent (Supervisor digests, run finished or failed notices) is mailed (`kind` digest | run) if `~/.paseo/agents-mail/endpoint.json` exists and `/api/health` answers (checked once a minute); otherwise, or if the mail fails, it is sent directly as before. Tasks, nudges, judgement calls, `supervisor_ask` and Inbox questions stay direct.
- **`excludePaths` / `excludeAgents` (Factory settings).** The Factory never lists, watches, digests or spawns an agent whose directory is inside an excluded path (default: none; matched by path, so an agent recreated with a new id stays excluded), and refuses to spawn there.

## Extensions

Another plugin registers with the Factory; it gets no sidebar row, only a Factory tab, and its tools join the `factory` MCP server:

```ts
const factory = (globalThis as any)[Symbol.for("paseo.factory")];
const unregister = factory.registerExtension({
  id: "my-extension", version: "1.0.0", tab: "My Extension",
  tools: [{ name: "my_status", description: "...", input: z.object({}), run: (input, call) => ({}) }],
  stageKinds: [{ kind: "my-kind", run: async (ctx) => ({ verdict: "ok", summary: "..." }) }],
  roles: [{ name: "my-runner", yaml: "name: my-runner\n..." }],
});
```

`ctx` carries `runId`, `stageId`, `params` (the stage's own fields, templates rendered), `vars`, `paseo`, `signal` and `services` (`spawn`, `leases`, `warden`, `inbox`; `factory.services()` gives the same outside a stage). Stage kinds must be idempotent: a running stage runs again after a restart. If the extension loads before the Factory, push the registration onto `globalThis[Symbol.for("paseo.factory.pending")]` (an array); the Factory drains it.

### Extensions in another plugin's process

Paseo runs each plugin's server in its own process, so `globalThis` registration only works for code inside the Factory's process. Other plugins register over the Factory's loopback endpoint (`~/.paseo/factory/endpoint.json`, bearer = its token) and serve a small loopback API of their own:

`POST /extensions/register` `{ id, version, tab?, callback: { url, token }, tools: [{ name, description, inputSchema, readOnly?, trustedWrite? }], rpc: [{ name, readOnly? }], stageKinds: [{ kind }], roles? }` (`callback.url` must be `http://127.0.0.1|localhost|[::1]`). Registration is idempotent: send it at start and again every minute or so; a Factory restart forgets everything and the next registration restores it. `POST /extensions/unregister` `{ id }` removes it.

An extension tool not marked `readOnly` is not offered to agents with a trusted label (`trustedLabels`), unless it is marked `trustedWrite: true`: such a tool is offered to trusted agents only, and hidden from every other agent. Each tool call carries `trusted` (`{ input, callerId, trusted }`), so the extension can check it again.

The Factory forwards, with `Authorization: Bearer <callback.token>`:
- `POST <callback>/tools/<name>` `{ input, callerId, trusted }` → `{ result }` (the tool is served under the `factory` MCP server with your `inputSchema`; validate the input yourself; an error status with `{ error }` becomes the tool error).
- `POST <callback>/rpc/<name>` `{ input, callerId }` → `{ output }` (for the tab, through `factory.extension.call`).

An rpc registered with `readOnly: true` (in-process or remote) is also reachable by other plugins on the Factory's loopback endpoint: `POST /extensions/<id>/rpc/<name>` `{ input }` → `200 { output }`, bearer = the endpoint token (`~/.paseo/factory/endpoint.json`), `callerId` `loopback`. Other rpcs answer 403, an unknown extension or rpc 404, input that fails the rpc's schema 400. Mark only rpcs with no side effect and no secret in the output; this is how one extension reads another's facts (for example the releaser's `ticket-facts`).
- `POST <callback>/stages/<kind>` `{ runId, stageId, blueprint, params, vars, outcomeToken }` → `{ outcome: { verdict, summary?, data? } }`, or `{ pending: true }` for a stage that waits: finish it later with `POST <factory>/stages/<outcomeToken>/outcome` `{ verdict, summary?, data? }` (bearer = the endpoint token; one use).
- `GET <callback>/health`: any HTTP answer counts as alive. After 3 consecutive unreachable calls or probes (probed once a minute) the extension is dropped.

Roles shipped by an extension and `ctx.services` are in-process only for now.

### Extension tab UI

Add `rpc: [{ name, input: zodObject, output: zodObject, run(input, call), readOnly? }]` to the registration: backend calls for your tab, validated with those schemas and reached through the Factory RPC `factory.extension.call({ id, name, input })`. In your client bundle register a component for the tab:

```ts
const queue = ((globalThis as any)[Symbol.for("paseo.factory.client")] ??= []);
const add = (id, Tab) => (Array.isArray(queue) ? queue.push([id, Tab]) : queue.registerTab(id, Tab));
add("my-extension", ({ theme, layout, extensionId, call }) => /* call("board", { ... }) */ null);
```

Until the Factory client has loaded, push `[id, Component]` onto that array; afterwards the global is the registry object and `registerTab(id, Component)` returns an unregister function. The component renders inside the extension's tab with `{ theme, layout, extensionId, call(name, input), open(link) }`; `open` leaves the tab for `{ tab: "blueprints", runId }` (the run, expanded), `{ tab: "inbox", itemId }` (the item, opened) or `{ url }` (http(s) only, in the browser); without one the tab shows the extension's metadata. It can use the host UI exports. Settings go through your own `rpc` entries (your server half reads and writes its own settings).

## Sidebar badge

On hosts with `client.addAgentBadge`, agents with the `paseo.factory` label show `<blueprint> · <stage>`; the tooltip has the run and the role. Hosts without the API are unaffected.

## Environment

`FACTORY_PORT` (default 47820), `FACTORY_DATA`, `FACTORY_ENDPOINT`, `FACTORY_BLUEPRINTS_DIR` (extra blueprint folder, first in precedence). Per-module scope variables are unchanged: `PASEO_WARDEN`, `PASEO_INBOX`, `PASEO_LEASES` = `off` to skip a module for an agent (`on` with the `opt-in` scope). `PASEO_WARDEN_INTERVAL` sets an agent's default check interval.

## Around a run: event mails, retro, janitor

Settings of the Blueprints module (`runs`, `events`, `retro`, `janitor`):

- **Event mails** (`events.mailTo`, default empty = off; e.g. `@pm`): one short mail (run id, stage, reason) when a run starts waiting on a gate or paused for a person, when a stage exhausts its attempts (this also covers the wait for the PM), and when a run fails or is aborted. A mail is sent once per event (keys are stored on the run). No mail for a run that goes well, nor for a failed child run (its parent reports).
- **Run notices** (`runs.notifyMailTo`, default empty = as before): the notice that a run is done, failed or aborted goes to the agent that started the run (and the run's PM) as a message, which can interrupt its turn. Set to an address or alias (e.g. `@pm`), the Factory sends ONE mail there instead (subject `Run <id> <ticket> done|failed|aborted`, body with run id, blueprint and vars) and no live message. A stage that needs the PM's judgement is mailed the same way (`Run <id> <ticket> needs PM`, with the `blueprint_retry` instructions) instead of spawning a PM (and no PM is spawned at any other judgement point). It only needs the address (Agents Mail), no coupling to any other plugin. The `events.mailTo` mails (waiting, exhausted, failed, aborted) are separate and unchanged, so the same address can receive both.
- **On-demand run PM** (while `runs.notifyMailTo` is empty): each judgement point spawns a short-lived PM (role `pmRole`, title `PM <blueprint> <run> · <point>`, label `paseo.factory.stage=pm`, env `PASEO_FACTORY_STAGE=pm`): an exhausted stage (`exhausted = "pm"`), a failed run (a child's failure is judged by its parent's PM), a gate with `pm = true`, and a paused run waiting for a resume decision. One PM per judgement key `<run>:<point>:<stage>:<entry>`, never a second for the same key; at most `pm.maxPerRun` (4) per run, then the human. Its prompt holds the point, the run's vars, PR facts and the retro's digest. It acts only through `blueprint_retry`, `blueprint_resume` (at most `pm_extra_max` extra attempts), `blueprint_abort` on its own run and its child runs, and `inbox_answer` on its own `pm = true` gate; it never starts a run. It finishes with `blueprint_pm_done` (handover=true hands the point to the human) and is archived with its workspace when its turn ends; a point it left open, a PM still deciding after `pm.timeoutMinutes` (10) or one that is gone goes to the human as before. Spend above `pm.maxUsd` (0.5) is flagged (`pm_over_budget`). When unsure it calls `blueprint_pm_escalate`: first `pm.escalateTo`, else the Supervisor (`supervisor_ask`) while it is enabled, else the Supervisor's `reportTo` by Agents Mail; after `pm.escalateTimeoutMinutes` (30) without an answer (`blueprint_pm_answer`), or called again, the human through a blocking `inbox_ask`. The run's waiting worker is told and marked waiting meanwhile. History events: `pm_spawned`, `pm_escalated`, `pm_answer`, `pm_escalation_timeout`, `pm_done`, `pm_handover`, `pm_timeout`, `pm_to_human`, `pm_ended`.
- **Retro** (`retro.*`): when any run ends (done, failed or aborted) the Factory computes a digest of its history (timeline, attempts and retries, gate waits, human versus agent time, review rounds, flakes such as exit 137 or pod start timeouts, spend) and starts a small separate agent (role `retro`, default Haiku, no repository; it runs on `retro.runtime`, empty = the Factory `runtime` setting) that mails `retro.mailTo` one short retrospective. `retro.mailTo` defaults to empty: no retro agent, no retro or janitor mail (e.g. `@user`). `retro.prompt` is the retro agent's prompt, a template with `{{run_id}}`, `{{mail_to}}` (= `retro.mailTo`) and `{{digest}}` (filled once, so a digest that contains braces stays as it is); the default asks for one mail of at most 15 lines: timeline, where time was lost, one or two Factory improvements, a kept worktree. A run that went straight through (nothing retried, nobody judged, under 15 minutes or a dependency bump) gets a three-line mail built without an agent (`retro.skipTrivial`). If the agent cannot start, the digest itself is mailed. `retro.maxUsd` flags a retro that cost more (it cannot cut a turn short); `retro.timeoutMinutes` gives up on a retro that never ends.
- **Archive with agent** (`archiveWorkspaceWithAgent`, default on): whenever an agent the Factory spawned is archived (by the Factory, by itself or by a person), its workspace (pod) is archived too, as long as a run created or joined it for it and no other live agent remains in it (the orphan sweep takes it later otherwise). Dirty or unpushed work does not keep it. One log line per archived workspace.
- **Verdict reminder and PM paging** (`verdictNudge`, `pm.pageOnExhausted`, both on by default): a worker that ends a turn without a verdict first gets ONE explicit "call your verdict now" reminder that uses no attempt (once per attempt); the next turn without one is an ordinary nudge and uses an attempt. An exhausted stage spawns the run's on-demand PM at once, also while `runs.notifyMailTo` is set; the mail then says which PM was paged.
- **Janitor** (`janitor.enabled`, `janitor.dryRun`): after the retro, archive the run's workers (every agent the Factory spawned for it) and their workspaces (pods). Every workspace is archived, dirty or not (the human rule: force the archive after the deletion of the agent, even if there is still code); `git status --short` is only traced into the run history (`janitor_trace`), with a 5 s timeout that never blocks, and only for a workspace one of whose agents was active in the last 5 min: on the Kubernetes Runtime a terminal in a suspended pod resumes it, so an idle worker's trace used to answer "no answer (5 s)" and wake a pod about to be deleted; it now says "not traced (idle N min ...)". With `dryRun` (the default) nothing is archived and the retro says what would be. Replaces `archiveOnFinish` when enabled.
- **Criteria reminder** (`gates.criteriaReminderMinutes`, default 30, 0 = off): an approval gate that has `criteria` (the ticket blueprint's acceptance-criteria gate) and is still unanswered after this many minutes sends one more "waiting" mail, "reminder n/3 ... still waiting N min", every N minutes, at most 3. It goes through the event mails, so it needs `events.mailTo` (default empty = no reminders) and nothing is hardcoded. There is deliberately no timed default: criteria are the human's sign-off on what QA checks, so a timeout never approves (or denies) them; the gate stays open.
- **QA `pending_merge`** (ticket blueprint): QA that can verify some criteria only once the PRs are merged or deployed answers `pending_merge` instead of `unable_to_verify`. The run goes to `wait-merge`, a `wait = "merge"` gate: no Inbox item blocks, the engine polls GitHub (`pollSeconds`) and a "waiting" mail (`events.mailTo`) says which PRs to merge. Merged (or a head that moved) runs QA again; after 8 h (`expires_in_minutes = 480`) it falls back to the `ask-blocked` gate as before. After a merge the PR babysitting stage is skipped (`skip_if` on the `wait-merge` verdict) and the `merge` gate, which completes by itself once GitHub shows the PRs merged, leads to the release request. The `qa` role of your roles git source should describe the `pending_merge` verdict.
- `{{from.stage}}`, `{{from.verdict}}`, `{{from.summary}}` in blueprint templates are the stage whose edge led to the current one (the `ask-blocked` gate uses them).

## Provider usage limits (`usageLimit`, Blueprints > Quota)

Off by default (`usageLimit.enabled`). Not the Kubernetes `exceeded quota` above: this is the model provider's usage limit.

- **Classifier** (`shared/blueprints/usage-limit.ts`, pure, also the read-only tool `usage_limit_classify`): only the terminal error of a failed turn (`PluginTurnOutcome.error`: `message` and `code`), never logs or timelines. A usage limit only on an explicit signal: `code` `rate_limit_error` / `rate_limit` / `usage_limit_reached` / `rate_limit_exceeded`, HTTP status 429, `API Error: 429 {...}` (or a JSON error type above), or the provider's own sentence anchored on the whole message (Claude Code "Claude AI usage limit reached|<epoch>", "... limit reached ... resets 3pm (Europe/Paris)"; Codex "You've hit your usage limit ... try again in/at ..."), with the reset time read from it (`resetZone` for a clock without a zone; past or more than 7 days ahead: none). Not a usage limit: 529/overloaded, other 5xx, network and DNS, auth, context too long, tool and permission errors, the Kubernetes quota, work failures. An error nobody classified takes the normal path and mails ONE alert per signature to `unknownAlertTo` (persisted), so the rules grow from evidence.
- **Run level:** a match holds the run (status `suspended`, shown as "paused: quota" with `resume_at`): no attempt, flake, nudge or Inbox item; the worker is kept and its pod suspended. It resumes at the reset time plus 60 s, else after `probeMinutes`, with a continue prompt ("the provider usage limit was lifted ..."). A cron run held this way is no failure of its schedule.
- **Whole Factory:** only a second independent match (another agent and run within `confirmMinutes`, default 15) or a probe (a throw-away one-turn agent on the daemon, label `paseo.factory.usage-probe=1`, model `probeModel` or the defaultProvider, 30 s after a first match, at most one every 5 minutes) holds every live run. While held: `blueprint_start` and the start form refuse, cron slots are skipped (not back-filled, no failure), no retro agent starts, the Supervisor is not woken automatically and Warden pings nobody.
- **Resume:** a non-LLM scheduler on the Blueprints tick probes at `resume_at`; still limited: the hold stays (next reset time, else 10, 15, 30 minutes); passed: runs resume `resumeConcurrency` (default 2) every `resumeStaggerSeconds` (default 60), oldest first. A person's own Factory-wide suspension (`blueprint_suspend all`) always wins: nothing resumes on its own while it is on.
- **Notify:** `usageLimit.notify` (addresses, aliases such as `@assistant`, `supervisor`): one mail on a global pause, resume and lift, with the held runs and their workers' agent ids, so an assistant can sweep agents outside the Factory ("continue" one by one) once it resumes. `usage_limit_status` (read-only, every agent; `PASEO_USAGE_LIMIT=off` skips it) gives state, `resume_at`, runs and agents for a heartbeat.
- **State and audit:** `usage-limit.json` in the Factory's data folder (outside any run, written atomically): the hold, the recent matches, the alerted signatures and an audit log of every run pause, global pause, probe, resume and lift (matched rule and evidence, reset time, runs). The Quota sub-tab (next to Crons) and a banner above every Factory tab show it, with **Lift pause** (RPC `blueprints.usage_limit.lift`; `usage_limit_lift` for trusted agents and the Supervisor).

## Infrastructure flakes (`flakeRetries`)

What counts as infrastructure is the Blueprints setting `flakes`: `patterns` (`{ pattern, label, startFailure }`, case-insensitive regular expressions, first match names the reason; `startFailure` marks a workspace that never came up, two in a row pause the run) and `retroPatterns` (what the retro digest names as flakes). The defaults are the Kubernetes Runtime's failures listed below; a gone provider session is always one. With the defaults, a worker that dies of infrastructure (exit 137/143, OOMKilled, "could not start the pod", "could not write bridge.mjs", "container not found", "channel ended", pod not ready, pod evicted/replaced, worker gone, "No conversation found with session ID" after a plugin reload or a recreated pod) is not a failed attempt: the Factory starts a fresh worker and pod without using `max_attempts`, up to `flakeRetries` times per stage entry (Blueprints setting, default 3; a stage's own `flake_retries` raises it). Each one is a `flake_retry` event with the matched reason. Past the bound they count as attempts again; when the stage then exhausts, the reason ends with `infra flakes ×N: <reasons>` (PM message, `exhausted` event mail), and the retro digest has an `Infra flakes retried for free` line. A worker whose provider session is gone ("No conversation found with session ID ...") is never re-sent to: it is archived and a fresh worker takes the same stage with a note, and a nudge that hit it does not use an attempt. A turn that ends without a verdict, a test failure or a normal verdict is never a flake.

## Suspending runs (`blueprint_suspend`)

Disabling the whole plugin to stop the Factory also removes the Inbox, Leases and Warden tools of every agent, and archiving worker workspaces does not hold (the engine respawns a worker for each running run within a minute). Suspend holds the runs instead:

- `blueprint_suspend({run} | {all: true}, reason, force?)`: the run gets status `suspended` (with `reason`, `since`, `by` and what happened to the pod in `blueprint_status`, the Blueprints tab and the Overview). No worker is spawned or prompted, no stage is retried, no attempt is used, no "could not start a worker" item is raised, the Warden watch of the stage ends, and open gates keep their Inbox items pending. The stage worker is kept (not archived); on Kubernetes its pod is suspended through the Kubernetes Runtime (`podAction` suspend, volume kept; a busy pod is refused unless `force`), a local worker is just not prompted. A verdict from a suspended run's worker is refused.
- `all: true` (trusted agents and the Supervisor only) also sets a Factory-wide suspension, persisted in the run store: `blueprint_start` and the start form refuse while it is on, and a plugin reload or restart does not replay suspended runs (they are outside the engine's active set).
- `blueprint_resume({run})` continues a suspended run at the same stage and attempt count: the pod is woken and the existing worker gets a "resumed" prompt, or, if it is gone, a fresh worker starts with the original prompt and a replacement note. A run that was `paused` goes back to paused. A gate answered meanwhile is taken then. `blueprint_resume({all: true, concurrency?})` lifts the Factory-wide suspension and resumes every suspended run, at most `concurrency` (default 2) at a time; it returns at once and the rest proceed in the background.
- Resuming or re-judging a run (`blueprint_resume`, a PM `blueprint_retry`, an answered escalation) withdraws the run's older pending escalation or pause items from the Inbox. A trusted agent may also withdraw any Factory-internal item (asker `blueprint:<run>`) with `inbox_withdraw`.
- The workspace runtime must offer the **workspace-control capability** to other plugins: `globalThis[Symbol.for("paseo.workspace-control")]` is a registry keyed by runtime id (the Factory `runtime` setting), each entry `{ suspend(workspaceId, { force }), wake(workspaceId) }` answering `{ ok, message?, busy? }`. Those two calls are all the Factory uses (suspend on `blueprint_suspend`, wake on `blueprint_resume` and before prompting a suspended worker). Without it the run is still held and the workspace is left to the runtime's own idle suspension (the reason is shown in `suspended.pods`). For one release the Factory also accepts a Kubernetes Runtime that only offers the older `globalThis[Symbol.for("paseo.kubernetes-runtime")].podAction(workspaceId, "suspend" | "resume", { force })`, for the `kubernetes` runtime only.

## One workspace per run (`shareWorkspace`)

Off by default. With the Blueprints setting `shareWorkspace` on, an agent stage marked `workspace = "run"` joins the run's workspace (pod) instead of creating its own: the first such stage creates it, later ones create their agent in it (`paseo.workspaces.ref(id).agents.create`). `ticket.toml` marks investigate, implement and babysit (the fix and qa-repair loops already reuse the implementer's agent); QA stays `new`, so it keeps an independent checkout and an OOM in its stack cannot take the implementer's worktree down. Each re-entry into QA is still a fresh worker and pod. If the shared workspace is gone when a stage starts, the worker gets a new one, which becomes the shared one. The janitor groups agents by workspace, so a shared pod is inspected once and archived after all its agents; a dirty one goes with them. A pod holds the pod's resources of the project profile, so size it for the heaviest stage it hosts.
